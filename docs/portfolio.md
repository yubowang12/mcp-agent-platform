# 求职材料：这个项目怎么讲

> 面向岗位：Agent 开发 / 后端开发（实习）。目标是在 60 秒内让面试官知道"你做过什么、怎么做的、效果如何"，并能扛住 3 轮追问。
> 项目定位：作品集项目（也可作为毕业设计备选），不是"课程作业"。

## 一句话版本

用 Java（Spring AI）实现了一个规划型 MCP Host，调度 Python Agent 与工具微服务；做过能力工具集重构、手写三态熔断与降级、以及 30 条任务集的量化评测。

## 简历条目（挑 3 条写，数字都可以当场复现）

1. 设计并实现基于 MCP 协议的多智能体编排平台（Java/Spring AI + Python MCP SDK）：Java Host 负责规划、调度与结果聚合，Python Agent 以 MCP 工具形式暴露能力；实现工具目录前缀化与双向映射、多步 ReAct 循环（最多 10 步）与超时保护。
2. 将 Agent 的"万能入口"重构为能力工具集（`summarize` / `translate` / `run_task`），用"写清不做什么"的工具描述与"规划器能自己答就不委派"策略，把写作类任务的模型调用从 3 次降到 1 次；5 条工具选择样本全部命中。
3. 手写三态熔断器（CLOSED / OPEN / HALF_OPEN）并接入工具调用链：熔断期间调用 **0ms 快速失败**（原本要等 45s 超时）；定义 `DEGRADED` / `errorCode` 降级口径，停掉一个下游服务时接口不返回 5xx。
4. 搭建 30 条任务集的批量评测（Python 标准库，无额外依赖），输出严格/宽松成功率、P50/P95 与失败模式分布；双组对照下严格成功 25/30（83.3%），并量化了"直通基线更快但无工具能力"这一取舍。

## 60 秒讲法（口述稿）

"我做了一个基于 MCP 协议的多智能体编排平台。核心是 Java 这边当'规划者'——它带一个 LLM，负责拆任务、选工具、汇总结果；Python 那边是执行器，把自己的能力按 MCP 协议暴露成工具。

做这个项目我主要解决了三个问题：一是工具选择，原来只有一个万能入口，模型只能盲选，我拆成了摘要、翻译这类专用工具，描述里写清'不做什么'，模型的选择准确率就上来了；二是故障治理，我手写了三态熔断，连续失败就快速拒绝，不再干等超时；三是评测，我设计了 30 条任务集，用脚本批量跑，能量化成功率和延迟，而不是只讲一个演示案例。"

## 3 分钟深入版（按"问题 → 做法 → 结果"讲）

1. **问题 1：只有一个万能工具，模型没法选。**
   做法：拆出 `summarize` / `translate` 两个专用工具，`run_task` 降级为兜底；描述按"用途 / 输入输出 / 不做什么"三段写。
   结果：5 条样本全命中；顺带发现"写自我介绍"被委派给弱模型，加了"写作类直答"规则后从 3 次模型调用降到 1 次。
2. **问题 2：下游挂了整个请求就崩。**
   做法：手写三态熔断（失败 3 次打开、冷却 30s、半开只放 1 个探测），包在超时器外层；失败判定改用 MCP 的 `isError` 异常而不是字符串前缀；任务级引入 `DEGRADED` 口径。
   结果：停掉工具服务，接口仍返回 200 + 降级答案；熔断后调用 0ms 返回。
3. **问题 3：怎么证明有效。**
   做法：30 条任务集（单步/两步/三步/越界/缺参各 6 条）+ 批跑脚本，严格成功按"状态 OK 且工具序列完全匹配"算。
   结果：严格 83.3%、宽松 90%；P50 2.7s；失败集中在"多步漏步"和"缺参不追问"。

## 高频追问与答法

| 问题 | 怎么答（要点） |
|---|---|
| 为什么用 MCP，不自己写 REST？ | 工具/能力标准化：新增一个 Agent 只要按协议暴露工具，Host 零改动就能发现（M1 加 `subtract` 时验证过）；REST 要自己定 schema 和发现机制 |
| 为什么熔断手写，不用 Resilience4j？ | 想自己掌握三态与半开的细节（冷却、清计数、并发探测），也为了可测；生产会选 Resilience4j，我在文档里写了对比与取舍 |
| 为什么熔断包在超时外面？ | 超时也是一次失败，必须计入熔断；反过来外层超时会把熔断的快速失败"吞掉" |
| 成功率怎么算？ | 严格 = `status=OK` 且工具序列完全匹配；宽松 = 答案非空且所需工具都调到；比较时剔除 `terminate`（控制动作，不是能力选择） |
| 30 条任务集怎么保证不是自欺欺人？ | 金标准先写死（期望工具序列），跑完不改；改口径时用 `--rescore` 重算而不重跑模型；原始 `raw.jsonl` 全部保留 |
| 最难/最坑的点？ | 两个：① 半开"何时探测"——没有流量就永远不恢复，最后选"真实请求触发"；② 换云端模型时 base-url 多带 `/v1` 导致 404，查了好久 |
| 如果重做会改什么？ | 先做评测再优化（这次是反过来的）；熔断换滑动窗口；补 MCP 会话重连 |
| AI 辅助的部分怎么算？ | 诚实说：AI 帮我写代码与文档，我负责需求拆分、方案取舍、验收标准与结果复核（这条写清楚反而加分） |

## 5 分钟演示脚本

1. `.\demo\start-dev.ps1` 起全套（8001 / 8002 / 8090）
2. `GET /api/catalog`：展示 7 个带前缀的工具
3. `POST /api/task` 跑三条：单步（现在几点）、三步（算完再翻译）、越界（查天气 → 明确说明做不到）
4. 停掉 8001，再打一次：看 `status=DEGRADED`、`errorCode=TOOL_ERROR`、`degradedSteps=[1]`
5. 再连打几次：看 `CIRCUIT_OPEN` 且 `latencyMs≈0`
6. 打开 `demo/eval/RESULTS.md`：讲成功率和 P95

## 已知不足（被问"哪里做得不够"时主动说）

- 下游**重启后熔断不会自动恢复**（MCP 会话失效），需要重启编排层；重连列在 R1。
- 熔断用**连续失败计数**，时好时坏的"翻转服务"不会触发。
- 评测 30 条、单次运行、**没有置信区间**；人工判定只抽样 10 条。
- 没有 CI、没有前端控制台。

## 下一步加分项（按性价比排序）

1. **GitHub Actions CI**：`mvn test` + 评测脚本冒烟，README 挂 badge——招聘方很看这个。
2. **前端控制台**：把 trace、`/api/servers` 健康状态可视化，演示效果最好。
3. **MCP 会话重连**：解决"重启后不恢复"，同时是 R1 注册中心的前置。
4. 补 `B-rule` / `B-llm-3b` 对照组，让"编排策略"的对比更完整。
