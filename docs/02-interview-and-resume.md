# 一、简历条目（4 条，挑 3 条写）

**① 设计并实现基于 MCP 协议的多智能体编排平台（Java/Spring AI + Python MCP SDK）**
> 主句：Java Host 负责**规划、调度、结果聚合**，Python Agent 以 **MCP 工具**形式暴露能力；实现**工具名前缀化与双向映射**、**多步 ReAct 循环**（最多 10 步）与**超时保护**。
> 会被问：为什么用 MCP？前缀化解决什么？ReAct 循环怎么退出？

**② 将 Agent 的"万能入口"重构为能力工具集，用工具描述与规划器策略把模型调用降为 1 次**
> 主句：拆出 `summarize`/`translate`，`run_task` 降级兜底；描述按"**做什么 / 不做什么**"写；加"**规划器能自己答就不委派**"规则；写作类任务模型调用 **3 次 → 1 次**，5 条工具选择样本 **5/5 命中**。
> 会被问：描述为什么写"不做什么"？怎么证明是描述起作用而不是运气？

**③ 手写三态熔断器并接入工具调用链，熔断期间 0ms 快速失败**
> 主句：**CLOSED/OPEN/HALF_OPEN**，连续失败 3 次打开、冷却 30s、半开只放 1 个探测；失败判定改用 **MCP `isError` 异常**而非字符串前缀；定义 **`DEGRADED`/`errorCode`** 降级口径，停下游服务时接口不返回 5xx。
> 会被问：为什么手写不用 Resilience4j？为什么熔断在超时外层？半开怎么放请求？

**④ 搭建 30 条任务集的批量评测，量化成功率与延迟**
> 主句：**5 类各 6 条**（单步/两步/三步/越界/缺参）+ 金标准；严格成功 = 状态 OK 且**工具序列完全匹配**；**严格 25/30（83.3%）、宽松 27/30（90%）**、P50 **2.7s** / P95 **7.3s**；与直通基线对比。
> 会被问：成功率怎么定义？为什么剔除 terminate？30 条够吗？

# 二、题库（按主题）

## A. 项目与架构 ⭐

**A1. 一句话介绍这个项目？**
Java 做规划型 Host（带 LLM，负责拆任务/选工具/聚合），Python 做执行器（把能力按 MCP 暴露成工具）；中间用 MCP 协议，另外做了熔断降级和 30 条任务集的评测。

**A2. 为什么拆成 Java + Python 两个服务？**
Java 生态适合做控制面（Spring AI、配置、Web、治理），Python 生态适合做 AI 能力（SDK、快速迭代）；MCP 恰好把"能力"标准化，语言不再是耦合点。

**A3. 为什么是"规划型 Host"而不是"Agent 自己规划"？**
早期版本（阶段 0）是哑转发：Java 把任务原样丢给 Agent，Agent 单轮回答。问题是**没有编排**——调度、治理、聚合都无处落地。改成 Host 自带规划 LLM 后，才有多步编排和可治理的调度点。

**A4. 一条请求的完整链路？**
`POST /api/task` → TaskController（校验/建上下文）→ Orchestrator 循环（调规划模型）→ 有 tool_calls 就执行 → 工具经过"熔断 → 超时 → MCP → Python" → 结果回填历史 → 再规划，直到无工具/步数上限/超时 → 组装 trace 落盘 → 返回。

**A5. 系统的边界在哪？哪里最容易坏？**
边界在 MCP 连接和模型 API。最容易坏的是 Python 服务（进程挂/重启）和模型限流；所以做了熔断 + 降级 + 结构化 trace。

**A6. 如果让你上线，先改什么？**
三件：① MCP 会话重连（现在服务重启后熔断不会自动恢复）；② 熔断换滑动窗口（现在翻转服务不会触发）；③ 加指标与告警（现在只有 JSONL）。

**A7. 这个项目你个人做了什么？**
诚实版：我负责需求拆分、方案取舍、验收标准、结果复核；AI 帮我实现和写文档。关键决策（工具描述写法、熔断放哪层、评测口径）是我定的，代码我逐段审过。

**A8. 为什么不用 LangChain / LangGraph / AutoGen？**
想自己实现一遍 ReAct 循环和工具调度，理解每一步在做什么；框架更适合快速堆功能，但会隐藏"步数、失败、降级"这些我需要在 trace 里量化的东西。（如果岗位要求框架经验，补一句：这套概念与 LangGraph 的 StateGraph 是对应的。）

## B. MCP 协议 ⭐

**B1. MCP 是什么？解决什么问题？**
Model Context Protocol，标准化"模型/应用"与"工具/数据源"之间的连接。解决 N×M 适配问题：每个工具不用给每个客户端写一套接口。

**B2. MCP 的三个角色？**
Host（承载 AI 应用，管多个 Client）、Client（与一个 Server 建立会话）、Server（暴露工具/资源/提示）。本项目：Java 编排层是 Host，内含 Client；Python 两个服务是 Server。

**B3. MCP 有哪三类能力？你用了哪些？**
tools / resources / prompts。只用 tools；resources 和 prompts 没用，sampling 明确不做（要 Server 反向借 Host 的模型，改造成本高）。

**B4. stdio 和 Streamable HTTP 怎么选？**
stdio 适合本地进程（客户端拉起服务、共享标准输入输出）；HTTP 适合独立部署的微服务（本项目两个 Python 服务各自监听端口，Java 通过网络连）。本项目选 Streamable HTTP。

**B5. 工具名为什么必须前缀化？**
function calling 的工具名要匹配 `^[a-zA-Z0-9_-]{1,64}$`，点号/空格/中文都非法；而且两个 Server 可能有同名工具，前缀能避免冲突。前缀用 `application.yml` 的 key（权威身份），不用 Server 自报的 `serverInfo.name`。

**B6. 前缀化之后怎么调用到正确的工具？**
给模型的工具名是 `demotools_get_time`，Host 内部维护"前缀 → (serverKey, 原名)"的映射，真正 `tools/call` 时还原成 `get_time` 发给对应 Server。**绝不把前缀发给 Server**。

**B7. MCP 的工具调用失败怎么表示？**
协议层是 `CallToolResult.isError`；Spring AI 的 `SyncMcpToolCallback` 在 `isError=true` 或传输异常时**抛 `ToolExecutionException`**。我们就是靠这个异常类型判失败，不靠错误文本。

**B8. 初始化握手做了什么？**
Client 发 `initialize`（协议版本、能力、客户端信息），Server 回自己的能力和 `serverInfo`，Client 再发 `initialized` 通知。握手失败 = 这个 Server 不可用（本项目的 fail-fast 就是卡在这）。

## C. Function Calling 与工具设计 ⭐

**C1. 模型怎么知道该调哪个工具？**
它只能看到工具名、描述、参数 schema。所以描述质量直接决定选择质量——这不是"写文档"，是"写接口"。

**C2. 描述里为什么要写"不做什么"？**
正面描述（"压缩文本"）无法排除近邻工具；写"不翻译、不查询、不处理图片"能直接切断错选，还能告诉模型"该用哪个替代工具"。

**C3. 参数默认值有什么用？**
减少"缺参失败"。比如 `max_words=100`，模型不传也能跑；同时也让 description 更容易写清边界。

**C4. schema 是谁生成的？**
Python 侧由 SDK 从类型注解 + 默认值生成（pydantic）；Java 侧直接读 MCP 返回的 `inputSchema` 转成 `ToolDefinition`。我们没有手写 JSON Schema。

**C5. 工具名有什么规范？**
动词短语、小写下划线、≤64 字符、只含字母数字下划线连字符。比如 `summarize`、`get_time`。

**C6. 一次返回多个 tool_calls 怎么办？**
框架会逐个执行；我们目前**串行**（`ToolCallingManager.executeToolCalls`），没上 `McpAsyncClient` 并行。串行的好处是 trace 顺序确定，坏处是延迟叠加。

**C7. 模型幻觉出一个不存在的工具名怎么办？**
前缀白名单 + `ToolCallback` 数组只含真实工具：执行时会解析失败，`isError`/异常路径会把它记成失败，模型收到错误后再换。不会把幻觉名字发给 Server。

**C8. 工具结果太长怎么办？**
trace 里只留 200 字预览（`preview`）；回给模型的是完整结果。长结果会占用上下文，这是后续可以优化的点（截断/摘要）。

**C9. 怎么让模型少调工具？**
两条规则在系统提示里：① "自己能完成的写作/解释/建议类任务直接回答"；② "最终答复只给结果，不要复述输入"。前者把 3 次调用压到 1 次。

**C10. 你的工具描述改过几版？为什么？**
三版：初版只写"做什么"；第二版加"不做什么"；第三版把语言锁定（"输出语言与原文一致"）从 user prompt 提到 system prompt——因为 3b 模型会把短中文摘要翻成英文。

## D. Agent 循环与编排 ⭐

**D1. 你的 ReAct 循环怎么实现的？**
手动循环：`while` 里调 `ChatClient` 拿 `ChatResponse`；有 `tool_calls` 就 `ToolCallingManager.executeToolCalls` 执行并回填历史；没有就结束。状态机语义：PLANNING → EXECUTING → OBSERVE → 再 PLANNING。

**D2. 为什么关掉框架的自动工具执行？**
`internalToolExecutionEnabled(false)`。自动执行拿不到每步的成败/耗时/被熔断，trace 和降级判定都做不了。

**D3. 循环怎么防死循环？**
三重：`maxSteps`（默认 10）、任务总超时（300s）、`terminate` 工具。另外重复调用同一工具没有专门检测，靠步数兜底。

**D4. 空答案怎么处理？**
先追加一条"请基于已有信息给出最终答复，不要调用工具"重试一次；仍空则用最后一条工具结果兜底，标 `DEGRADED` + `EMPTY_ANSWER`。

**D5. 什么时候调 terminate？**
模型判断任务完成或无法推进时调用；我们把它当控制动作——不进评测的"能力选择"比较。

**D6. 多步任务的中间结果怎么传？**
靠对话历史：`executeToolCalls` 返回的 `conversationHistory` 直接替换 `ctx.messages`，下一轮模型能看到工具结果。

**D7. 为什么每步只允许一个工具？**
提示词里明确要求；一是 3b/7b 同时选多个容易乱，二是串行执行下多调并不会更快。

**D8. 任务上下文为什么单独一个类？**
`TaskOrchestrator` 保持无状态单例，所有请求级状态放 `TaskContext`，并发天然隔离，也方便测试直接构造。

## E. 并发、超时与线程

**E1. 工具超时怎么做的？**
提交到独立线程池 + `Future.get(45s)`；超时 `cancel(true)` 并返回超时文本。线程池是 daemon，独立于 Tomcat 线程。

**E2. LLM 调用超时怎么做的？**
同样的套路：独立线程池 + `get(60s)`，超时抛 `LlmTimeoutException`，由 `run` 统一转成 `TIMEOUT/LLM_TIMEOUT`。

**E3. `Future.cancel(true)` 真能停掉请求吗？**
只能中断线程；HTTP 客户端未必响应中断。所以是"尽力而为"，真正的回收靠连接池/请求超时。

**E4. 线程池为什么用 cached？**
工具调用是 IO 密集且耗时差异大（时间工具 40ms，Agent 调模型 10s）；cached 按需扩容，避免固定池被长调用占满。风险是无上限，生产要配 `maximumPoolSize` + 队列。

**E5. 同一请求的线程模型？**
Tomcat 请求线程跑循环；工具调用提交到 `tool-timeout` 池；LLM 调用提交到 `llm-call` 池。旁路记录用 `ThreadLocal`，所以只在请求线程上累积。

**E6. 如果两个请求并发，trace 会串吗？**
不会：`TaskContext` 每请求一个；`TraceRecorder.append` 是 `synchronized`；`ToolCallRecorder` 是 ThreadLocal。

## F. 熔断与降级 ⭐⭐

**F1. 熔断器三个状态？怎么迁移？**
CLOSED（放行、数连续失败）→ 连续失败 ≥3 → OPEN（拒绝）→ 冷却 30s 到期、下一个请求 `tryAcquire` → HALF_OPEN（只放 1 个探测）→ 成功 → CLOSED；失败 → 回 OPEN 且冷却从此刻重算。

**F2. 为什么必须手动清零计数？**
只在**状态切换**时清（进 HALF_OPEN、回 CLOSED）。如果探测期间清零，永远攒不够"成功 N 次"的证据；如果回 CLOSED 不清，旧失败会让它立刻再次熔断。

**F3. 半开为什么要限制并发？**
防止恢复瞬间一批请求涌进去把刚起来的服务再打挂；默认只放 1 个。

**F4. 半开探测由谁触发？**
冷却到期后由**下一个真实请求**触发（惰性），没有定时器。代价：没流量时状态一直 `OPEN`。

**F5. 为什么不做主动探测？**
要挑工具、造参数，参数不合法会"假失败"，把健康服务判死。真要做，用 `listTools()`（无参数、幂等）而不是业务工具。

**F6. 为什么手写，不用 Resilience4j？**
要能讲清三态与半开细节、要能注入假时钟做单测；库更适合生产。生产化时我会换，并把"滑动窗口/慢调用比例"一起带上。

**F7. 熔断粒度为什么按 server？**
同一 Server 的工具共享进程/网络/模型——`summarize` 挂了 `translate` 大概率也挂。工具多不是理由，**故障相关性**才是。

**F8. 为什么熔断包在超时外面？**
超时也是一次失败，必须计入熔断；反过来外层超时会把熔断的快速失败包住，而且超时异常到不了熔断器。

**F9. 熔断打开后，模型还能看到这个工具吗？**
能。我们**没有**把工具从目录摘除——因为摘除后就没有请求去触发半开，永远恢复不了。现在的做法是"调用时 0ms 拒绝"。

**F10. `TOOL_ERROR` 和 `CIRCUIT_OPEN` 有什么区别？**
前者是真调用了、真失败；后者是没调用、被熔断器拦住（`latencyMs≈0`）。后者才是"熔断生效"的证据。

**F11. 降级到底做了什么？**
三件事：工具失败不抛 500、把错误回填给模型让它换工具；规划器不可用时有兜底答案；任务级用 `DEGRADED` + `errorCode` 标记"带伤产出"。

**F12. 你的熔断有什么已知缺陷？**
两个：① 服务重启后 MCP 会话失效，探测必失败，需要重启编排层（重连没做）；② 连续失败计数对"时好时坏"的服务无效（成功即清零），M6 里规划了滑动窗口对照。

## G. 可观测性

**G1. trace 记了什么？**
每请求一行 JSONL：taskId、task、status、model、maxSteps/usedSteps、起止时间、总耗时、finalAnswer、steps[]（工具、参数、ok、耗时、错误码）、degraded、errorCode、degradedSteps。

**G2. 为什么用 JSONL 不用数据库？**
本地项目、要能直接用脚本读；一行一条，追加写不会破坏已有数据；M6 的评测脚本直接读它。

**G3. 落盘失败会怎样？**
只 warn 日志，不影响任务返回——trace 是辅助数据，不能拖垮主流程。

**G4. 怎么定位一次慢请求？**
看 `totalLatencyMs` 和每步的 `llmLatencyMs` / `latencyMs`：如果 `llmLatencyMs` 大，是模型慢；如果 `latencyMs` 大，是工具/下游慢。

**G5. 有指标（metrics）吗？**
没有 Micrometer；目前只有 JSONL + `/api/servers` 的健康状态。生产要补 QPS/错误率/熔断状态指标。

**G6. `/api/servers` 返回什么？**
每个 Server 的名字、版本、`healthy`、`state`（CLOSED/OPEN/HALF_OPEN）、`consecutiveFailures`。

## H. 评测 ⭐

**H1. 成功率怎么定义？**
严格 = `status=OK` 且工具序列完全匹配且答案非空；宽松 = 答案非空且金标准里的工具都调到了。前者口径干净（OK 蕴含全步骤成功），后者看出"抓到了但有多余动作"。

**H2. 为什么剔除 terminate？**
它是编排层的控制动作（结束任务），不是能力选择；不剔除会把"正确拒绝"判成失败（o3/o4）。

**H3. 30 条任务集怎么设计的？**
5 类各 6 条：单步、两步、三步、越界（应拒绝）、缺参（应追问）。每类考一个不同的能力，避免全在测同一个点。

**H4. 怎么保证评测不是自欺欺人？**
金标准先写死；改口径用 `--rescore` 重算而不重跑模型；`raw.jsonl` 全量保留可复查；抽样 10 条人工判定。

**H5. P95 为什么比均值重要？**
均值会被少数极慢样本稀释；P95 反映"大多数用户会遇到的慢"，也是 SLO 常用的口径。

**H6. 你最大的失败模式是什么？**
三类：多步任务漏步/合并（h3）、重复调用（t3）、缺参不追问反而瞎编（m4/m6）。最严重的是越界硬套工具导致幻觉（o1：查天气调 `run_task`，编出温度）。

**H7. 直通组什么结果？为什么更快？**
P50 1.2s（vs 2.7s），因为它只有一次模型调用、没有工具往返；代价是时间/算术/翻译这类任务它只能"编"，没有真实工具结果。

**H8. 30 条够吗？**
不够做统计显著性，够做方向性对比。样本量、多次运行、置信区间是已知不足，写在结果文档里。

**H9. 为什么不 LLM-as-judge？**
同一个模型给自己打分会有偏差，而且要多花钱；这个项目的判定主要是"工具序列 + 状态"，本来就是可自动判的。

**H10. 如果重做评测会改什么？**
先写评测再写功能（这次是反的）；增加"重复 3 次取中位数"；补 B-rule/3b 对照组。

## I. Java / Spring

**I1. `SyncMcpToolCallbackProvider` 干了什么？**
把 MCP 的 `tools/list` 结果转成 Spring AI 的 `ToolCallback` 数组，名字用前缀生成器处理。

**I2. `@ConfigurationProperties` 记录类怎么绑定的？**
`@ConfigurationPropertiesScan` 扫到 record，按构造参数名做宽松绑定（`failure-threshold` ↔ `failureThreshold`），`@DefaultValue` 给默认值。

**I3. 为什么用 record 做配置？**
不可变、构造即校验、少样板代码；Spring Boot 3 支持构造器绑定。

**I4. Bean 的创建顺序这里有什么坑？**
`TaskOrchestrator` 构造时要拿 `List<McpSyncClient>`（自动配置产物）和 `CircuitBreakerRegistry`；后者依赖 `CircuitBreakerProperties`。如果配置没绑定，启动就失败——这次换成 DashScope 时正好踩了"key 没配 → 启动失败"。

**I5. 为什么 `TaskOrchestrator` 是单例却线程安全？**
它没有可变字段；所有请求状态在 `TaskContext`。`tools` 数组构造后只读。

**I6. `ToolCallingManager.executeToolCalls` 做了什么？**
按名字从 `ChatOptions` 的工具列表里找到回调、执行、把结果包成 `ToolResponseMessage`，返回新的对话历史。

**I7. 为什么用 `OpenAiChatOptions` 而不是通用 `ChatOptions`？**
需要设置 `model`、`toolCallbacks`、`internalToolExecutionEnabled(false)`；OpenAI 兼容厂商都能用这个。代价是绑定了 OpenAI 生态，换厂商要改类型。

**I8. 有没有考虑过响应式（WebFlux）？**
没有。当前是同步阻塞模型（`McpSyncClient` + `ChatClient.call()`），简单够用；要高并发再换异步。

## J. Python / MCP SDK

**J1. `@mcp.tool()` 做了什么？**
把函数注册进工具表；从签名和类型注解生成 `inputSchema`；把 docstring 或显式 `description` 作为描述。

**J2. 为什么用常量写描述而不是 docstring？**
`__doc__` 带函数体缩进，会原样发给模型；显式 `description=` 更干净。

**J3. Agent 内部又调了一次模型，算不算"套娃"？**
算一次委派：Host 规划 → Agent 执行。我们在 M4 之后规定"写作类任务由 Host 直接答"，就是为了避免没必要的二次调用。

**J4. 三个服务如何发现彼此？**
目前是 `application.yml` 静态配置（Host 连 8001/8002）；动态注册发现是 R1 的事。

**J5. Python 侧怎么拿 Key？**
优先级：`LLM_API_KEY` → `DASHSCOPE_API_KEY` → 读 Java 的 `application-local.yml`（就为了"一处配置"）。

## K. 系统设计延伸

**K1. 要支持 100 个 Agent 怎么改？**
加注册中心（服务发现 + 心跳 + 能力目录）→ Host 按能力路由；工具表按域分组（先选域再选工具）；客户端连接池化。

**K2. 怎么防止提示注入？**
工具描述里约束边界；Host 只信工具的结构化结果；不把用户输入当"系统指令"；真正的防护（白名单、沙箱、输出过滤）是 R3。

**K3. 多实例部署，trace 怎么办？**
按实例分文件（`{instance}-{date}.jsonl`）或直接写日志采集（OTel）；`synchronized` 只保证单进程内不交错。

**K4. 怎么做限流？**
网关/入口层令牌桶；保护自身与下游。本项目没做，属 R1。

**K5. 任务要跑 10 分钟怎么办？**
`/api/task` 同步会超时；改成提交任务 + 轮询/SSE 推送，trace 增量写。

**K6. 模型换了怎么保证行为不变？**
固定温度、固定提示词、任务集回归、对比评测；这次换 DashScope 就重跑了 24 个测试。

## L. 尖锐问题（"拷打"）⭐⭐

**L1. 这代码是 AI 写的吧？**
是 AI 辅助的，但设计决策和验收是我做的：工具描述为什么这么写、熔断放哪层、评测口径怎么定，这些都能讲；代码我逐段审过，也复现过故障场景。（诚实 + 能讲细节，比否认强。）

**L2. 你这个和 LangChain 的 Agent 有什么区别？**
框架把循环、工具、记忆都封装了；我是手写，所以能控制"每步只调一个工具、失败算不算降级、熔断在哪层"。本质是同一套概念。

**L3. 30 条任务集是不是太少？**
做方向性对比够用，做统计显著性不够。我已经在结果里标注了样本量、单次运行、无置信区间——这是已知不足，不是隐瞒。

**L4. 成功率 83% 是不是不高？**
按严格口径（工具序列完全匹配）83% 已经不低；失败集中在"多步漏步"和"缺参不追问"，两类都可归因、可改。宽松口径 90%。

**L5. 你的熔断真能恢复吗？**
现在不能自动恢复（MCP 会话失效），需要重启编排层；这是已知限制，重连在 backlog。**不要硬答"能"**——被追问演示会翻车。

**L6. 为什么不用 Kubernetes / Docker？**
单机项目，开发机没有 Docker；现在用脚本起进程。容器化是下一步。

**L7. 你怎么证明工具描述起了作用？**
对照：改描述前 3/5 命中，改后 5/5；另外"自我介绍"案例从 3 次调用降到 1 次，有 trace 时间戳。

**L8. 如果模型乱调工具，你怎么兜底？**
步数上限 + 工具失败回填 + 熔断快速失败 + 空答案降级；最外层还有任务超时。

**L9. 你的系统最脆弱的点？**
启动期：任一 Python 服务没起，Java 就起不来（fail-fast）。运行期反而更稳（熔断/降级）。这个取舍是刻意的，也在文档里写明。

**L10. 让你现在重构，你会先动哪？**
把"连接管理"抽出来（现在 MCP 客户端是 Spring AI 自动配置给的，重连做不了）；顺带把工具目录缓存和健康状态统一到一处。

# 四、答题策略

1. **先说结论，再说原因，最后给证据。**（"我们没做工具摘除，因为摘除后收不到请求、永远无法恢复；证据是停服实验里状态一直停在 OPEN。"）
2. **不会就说到边界。**"这块目前没做，我知道它属于 R1 的重连/注册中心；如果要补，我会先从连接管理抽起。"
3. **主动说失败案例**，尤其是 o1（越界硬套工具导致编造天气）——它同时展示了你的评测能力和对幻觉的理解。
4. **被问"为什么"时，给取舍而不是对错**："手写熔断是为了可控和可测，代价是没有滑动窗口；生产我会换成 Resilience4j。"
5. **数字要能被追问**：说到 83%，就要能立刻说出"25/30、严格口径、剔除了 terminate"。
