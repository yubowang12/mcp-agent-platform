## 1. 项目概述

### 1.1 背景

大语言模型（LLM）Agent 正从"单体应用"向"多智能体协作"演进，但在工程实践中存在三个突出问题：

1. **集成碎片化**：每个 Agent 厂商、每个工具生态各写一套接口，客户端接入成本高（N×M 适配问题）；
2. **缺乏统一协议与治理**：Agent 之间如何发现彼此、如何调度、故障如何隔离，没有工程化标准答案；
3. **单机瓶颈**：单体 Agent 无法水平扩展，难以支撑多任务并发。

MCP（Model Context Protocol）的出现为"工具/能力标准化暴露"提供了开放协议，本项目在此基础上进一步解决"Agent 集群化部署与治理"问题。

### 1.2 项目目标

**工程目标**：设计并实现一个可运行的 Agent 集群平台，具备：

- 工具与 Agent 的**微服务化**封装（统一 MCP 协议）
- Agent 的**注册发现、编排调度、容错治理**
- 任务执行的**全链路可观测**
- **异构多语言**协同（Java 编排 + Python 执行）

**论文目标**：围绕平台设计提炼 2~3 个创新点（调度算法 / 容错机制 / 安全沙箱），并通过实验数据证明有效性。

### 1.3 术语表

| 术语 | 说明 |
|---|---|
| MCP | Model Context Protocol，模型上下文协议，标准化 AI 工具/资源/提示暴露的开放协议 |
| Host | 承载 MCP Client 的应用程序（本项目为 Java 编排层与 Python Agent 运行时） |
| Client | 与 Server 建立 1:1 会话、负责协议通信的组件 |
| Server | 暴露工具/资源/提示的 MCP 服务端（本项目为 Python 微服务） |
| 工具（tools） | 可被调用的函数能力（本项目全部通信基于 tools） |
| Agent | 绑定 LLM、具备工具调用与任务执行能力的智能体 |
| 编排层 | 负责任务分解、调度分发、结果聚合的中心控制面 |
| 治理 | 注册发现、健康检查、负载均衡、熔断限流、降级的统称 |

## 2. 需求分析

### 2.1 用户与角色

| 角色 | 职责 | 主要操作 |
|---|---|---|
| 平台操作员 | 提交任务、查看执行结果与平台状态 | 前端控制台 |

### 2.2 功能需求

| 编号 | 需求 | 说明 | 优先级 |
|---|---|---|---|

| FR-2 | Agent 注册与发现 | Agent 启动时自动向注册中心注册能力；编排层动态发现可用 Agent | P0 |
| FR-3 | 任务编排调度 | 复杂任务拆解为子任务，按能力匹配 + 负载 + 成功率选择 Agent 执行 | P0 |
| FR-4 | 集群治理 | 健康检查（心跳/探活）、超时重试、熔断降级、负载均衡 | P0 |
| FR-5 | 可观测性 | 任务链路追踪（Trace）、Agent 调用日志、性能指标采集 | P1 |
| FR-6 | 前端控制台 | Agent 列表/状态、任务提交与追踪、调用链路可视化、评测面板 | P1 |
| FR-7 | 安全沙箱 | 工具调用权限控制、执行隔离、提示注入防护 | P2 |

### 2.3 非功能需求

| 编号 | 需求 | 指标（目标值，待实测校准） |
|---|---|---|
| NFR-1 | 响应性能 | 单任务端到端延迟 ≤ 模型推理时间 + 编排开销（< 500ms） |
| NFR-2 | 可用性 | 单 Agent 故障不导致平台不可用；故障自愈（自动摘除 + 重连） |
| NFR-3 | 可扩展性 | 支持水平扩容 Agent 实例；新增 Agent 类型无需改动编排层代码 |
| NFR-4 | 可维护性 | 模块清晰分层、配置外置、关键路径有日志与 Trace |
| NFR-5 | 资源成本 | 均使用开源组件 + 本地 LLM（Ollama），零持续服务费用 |

### 2.4 约束条件

- 毕设周期约 6 个月，中期检查约在第 3 个月；
- 无付费 LLM API 预算，统一使用本地 Ollama（qwen2.5:3b / 7b）；
- 开发机为单机 Windows，无 Docker，部署以本地进程为主；
- 单人开发，需控制工作量与依赖复杂度。

## 3. 总体架构设计

### 3.1 设计原则

1. **协议统一**：集群内一切跨进程通信（Java↔Agent、Agent↔工具）统一使用 MCP 协议，杜绝自定义私有接口；
2. **服务自治**：每个工具/Agent 独立进程、独立部署、独立扩缩容，故障互相隔离；
3. **中心编排、可治理**：编排决策集中在 Java 控制面，换取调度、熔断、追踪的统一性与可解释性（拓扑对比见 4.1）；
4. **异构解耦**：Java 负责"治理与编排"（强类型、工程成熟），Python 负责"Agent 智能"（AI 生态丰富），二者仅通过 MCP 协议耦合；
5. **可观测优先**：每个请求携带 Trace ID，贯穿 Java → Agent → 工具全链路。

### 3.2 分层架构

```
┌──────────────────────────────────────────────────────────────┐
│ L1 交互层    Vue 控制台（任务提交 / Agent 监控 / 链路可视化）    │

│ L2 编排治理层 Java Spring Boot（Host + Client）                │
│   ┌─────────┬─────────┬─────────┬─────────┬──────────────┐    │
│   │ 认证网关 │ 注册中心 │ 编排调度 │ 治理(熔断/限流/降级) │ 可观测性(Trace) │
│   └─────────┴─────────┴─────────┴─────────┴──────────────┘    │
├──────────────────────────────────────────────────────────────┤
│ L3 执行层    Python Agent 微服务（MCP Server + Client）        │
│   每个 Agent = LLM 绑定 + 工具集 + 任务执行循环                 │
│   ┌───────────┐ ┌───────────┐ ┌───────────┐                  │
│   │ Agent 研究型 │ │ Agent 执行型 │ │ Agent 审校型 │   ...       │
│   └─────┬─────┘ └─────┬─────┘ └─────┬─────┘                  │
│         │ MCP         │ MCP         │ MCP                     │
│   ┌─────▼─────┐ ┌─────▼─────┐ ┌─────▼─────┐                  │
│   │ 工具微服务  │ │ 工具微服务  │ │ 工具微服务  │  (get_time/搜索/SQL/代码执行...) │
│   └───────────┘ └───────────┘ └───────────┘                  │
├──────────────────────────────────────────────────────────────┤
│ L4 模型层    Ollama 本地推理（qwen2.5 等，OpenAI 兼容接口）     │
└──────────────────────────────────────────────────────────────┘
```

## 4. 核心设计

### 4.1 MCP 角色与拓扑设计

**角色映射**：

| 角色 | 本项目实体 | 说明 |
|---|---|---|
| Host | Java 编排层进程 | 创建/管理所有 MCP Client |
| Client | `McpSyncClient`（每个连接一个） | 与单个 Server 1:1 会话 |
| Server | Python Agent 微服务、工具微服务 | 暴露 tools |

**拓扑方案对比**（设计决策依据，论文可展开）：

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 中心编排（Java 统一调度） | 可治理、可追踪、可解释 | 编排层需高可用设计 | ✅ 采用 |
| 对等 Agent 互联 | 无中心单点 | 协作链路不可控、难熔断、难审计 | ❌ 不采用 |
| 层级 manager-agent | 分工清晰 | 总控 Agent 是瓶颈与单点 | ❌ 仅局部采用（任务分解可用 manager 思路，但调度权仍在 Java 层） |

**跨语言通信契约**：Java 与 Python 之间**只使用 MCP 标准协议**，不引入任何私有 RPC；Python Agent 与工具微服务之间同样走 MCP。这保证任何一侧的技术栈可替换。

### 4.2 Agent 设计

**Agent 定义**：`Agent = LLM 模型 + 系统提示词 + 工具集 + 执行循环`

**执行循环（ReAct 风格）**：

```
接收任务 → [思考] → 是否需要调用工具？
    ├─ 是 → 选择工具 → 调用（MCP tools/call）→ 观察结果 → 回到思考
    └─ 否 → 生成最终答案 → 返回
```

**Agent 分类**（规划）：

| 类型 | 职责 | 工具集示例 |
|---|---|---|
| 研究型 | 信息收集、资料检索 | 搜索、网页抓取 |
| 执行型 | 操作类任务 | 数据库、文件、代码执行 |
| 审校型 | 质量检查、结果复核 | 规则校验、二次推理 |
| 编排型（可选） | 复杂任务拆解（交由 Java 调度器协同） | 任务分解工具 |

**Agent 能力声明**：每个 Agent 在注册时声明 `能力标签 + 可用工具清单 + 性能画像`（成功率的滑动统计），供调度器选择。

### 4.3 服务注册发现设计

**现状（demo）**：静态配置写死 IP/端口，启动时强连接、fail-fast（已验证：Python 未启动时 Java 启动失败）。

**目标方案**：

```
Agent 启动 ──注册(能力/地址/端口)──▶ 注册中心
Java 调度器 ──订阅变更──▶ 拿到活 Agent 列表 ──建立 MCP 连接
Agent 心跳 ──每 N 秒──▶ 注册中心（超时未心跳 → 摘除）
```

**方案选型**：
- 起步：Java 内存注册表 + 定时心跳（简单、可演示）
- 进阶：Redis 做注册表与心跳 TTL（可多实例共享、更接近真实微服务）
- 不引入 Spring Cloud Eureka/Consul 全家桶（毕设范围控制）

### 4.4 编排调度设计

**调度目标**：为每个子任务选择"最合适"的 Agent 实例。

**调度决策因子**（创新点候选，可做对比实验）：

| 因子 | 说明 |
|---|---|
| 能力匹配 | Agent 能力标签与子任务类型匹配度 |
| 当前负载 | 在途任务数 / 队列长度 |
| 成功率画像 | 最近 N 次任务成功率的滑动平均 |
| 延迟画像 | 平均响应时间 |
| 成本（可选） | token 消耗估算 |

**调度算法（规划，论文创新点之一）**：加权评分法 `score = w1·匹配度 + w2·(1-负载率) + w3·成功率 + w4·(1/归一化延迟)`，与基线（轮询 / 随机 / 固定）做 A/B 对比实验。

**任务分解（简化方案）**：由 Java 层调用一个"任务规划"提示词或者简单规则引擎，将复杂任务拆成子任务 DAG（如：检索 → 生成 → 审校），按依赖顺序执行。

### 4.5 容错设计

| 机制 | 触发条件 | 行为 | 对应需求 |
|---|---|---|---|
| 超时 | 单次 MCP 调用超过阈值 | 中断调用，记为失败 | NFR-1 |
| 重试 | 连接类失败（如 ConnectException） | 指数退避重试 N 次 | NFR-2 |
| 熔断 | 某 Agent 连续失败 M 次 | 打开熔断，路由到备用 Agent | NFR-2 |
| 降级 | 无可用 Agent | 返回降级结果 / 转人工提示 | NFR-2 |
| 重连 | 心跳检测到 Agent 恢复 | 重新建立 MCP 连接 | NFR-2 |

> 现状验证：已实测"Agent 不可用时 Java 启动失败"，这是 fail-fast 行为的证据；容错机制落地后需重新实验对比（前后对比数据即论文素材）。

### 4.6 可观测性设计

1. **Trace**：前端生成 traceId → Java 编排层记录 → 通过 MCP 工具参数透传到 Agent → 工具微服务 → 全链路日志聚合；
2. **指标**：任务数、成功率、P50/P95 延迟、Agent 负载、熔断次数；
3. **前端可视化**：任务链路时序图、Agent 状态面板、评测对比图表（ECharts）。

### 4.7 安全设计（P2，规划）

1. **工具权限隔离**：每个 Agent 只允许调用白名单内的工具；
2. **执行沙箱**：高风险工具（代码执行、文件写入）在受限环境运行；
3. **提示注入防护**：工具返回内容做净化、系统提示词加固；
4. **接入鉴权**：网关层 API Key / JWT（毕设可简化）。

## 6. 关键流程时序

### 6.1 任务执行全流程（目标形态）

```
前端 ──POST /api/tasks──▶ 编排层
编排层 ──查注册中心──▶ 选择 Agent（能力匹配/负载/成功率）
编排层 ──tools/call run_task──▶ Agent 微服务 (MCP)
Agent ──[ReAct 循环]──▶ 工具微服务 (MCP tools/call) ──▶ 返回
Agent ──结果──▶ 编排层
编排层 ──更新任务状态/指标──▶ 前端 (轮询或 WebSocket)
```

### 6.2 Agent 上线注册流程

```
Agent 启动 → 读取配置(能力/模型) → 连接注册中心 → 注册(心跳线程启动)
编排层 定时拉取/订阅变更 → 发现新 Agent → 建立 MCP 连接 → 拉取 tools/list
```

### 6.3 故障处理流程

```
Agent 崩溃/超时 → 编排层捕获异常 → 记失败、触发重试策略
    ├─ 重试失败 → 熔断打开 → 从注册中心摘除/标记 FAULTY
    ├─ 任务有备用 Agent → 降级路由到备用 Agent
    └─ 无备用 → 任务标记 DEGRADED，前端提示
Agent 恢复 → 心跳恢复 → 注册状态 ONLINE → 编排层重连 → 熔断关闭
```

## 8. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 本地 LLM 推理慢、不稳定 | 实验数据质量、演示效果 | 用 qwen2.5:3b 控制延迟；评测任务使用 mock LLM 可复现 |
| 注册中心/调度算法实现超预期 | 中期检查进度 | 分级交付：内存注册表先行，Redis 后置；算法先用简单加权 |
| 熔断/降级缺少真实故障场景 | 论文实验说服力 | 主动故障注入（停服务、超时、随机失败）构造实验 |
| 论文创新点不足 | 答辩评分 | 提前锁定"调度算法对比实验 + 容错前后对比 + 安全沙箱"三个实验素材 |
| 时间管理失控 | 整体延期 | 每两周检查里程碑；论文框架可提前并行撰写 |
