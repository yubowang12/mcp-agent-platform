## 项目概述

个人项目，目标是做一个"可解释、可降级"的 Agent 编排层：Java 侧负责规划与工具调度，Python 侧以 MCP 微服务的形式提供工具与执行能力。项目从零实现了 ReAct 循环、工具名前缀化、超时与熔断包装、结构化 trace，以及带向量召回的长期记忆；技术栈为 Java 17、Spring Boot 3、Spring AI、MCP、SQLite 与 DashScope。

## 技术难点

最大的难点是"不可靠组件的编排"：模型会漏步、多调、编造参数，工具会超时或被熔断，而这些失败在字符串返回里分不开，最初只能靠扫错误文本猜，误判很多。我的做法是把失败判定从"扫错误文本"改成"记录可判定的事实"——包装器在调用过程中把成功、失败、超时、熔断写进请求线程的旁路记录，编排器每轮结束统一取走并写入 trace，再用固定前缀标识工具错误；同时规定任一步骤失败但仍有答案时任务标记为 DEGRADED，这样"有产出"和"全成功"在指标上就能区分开，评测时也不会把降级样本算成成功。为了验证这套判定，我补了一组故障注入测试：手动让某个 MCP 服务返回 isError、让它超时、让它不可达，分别断言 trace 里的状态码与任务最终状态。记忆层部分我踩过一个典型坑：同一事实被写了两份，语义记忆存原句、会话摘要又抄了一遍任务原文，结果过期语义记忆之后，摘要仍能把邮箱带出来，等于"忘了但没完全忘"；后来把摘要改成只记"做了什么 + 结论"（工具、步数、结果状态），内容统一归语义记忆管，并补了一条端到端回归测试固定这个行为。这件事让我意识到，记忆系统的难点不在写入，而在"删除是否彻底"。另外，我把工具描述当成一等公民来治理：每个工具的 description 都写清适用场景与"不做什么"，并在联调时用一组越界问题验证模型不会错选；工具名统一加服务前缀，避免多服务重名。上线前还做了一次故障演练：把 agent-worker 停掉，确认 Host 能在 3 秒内超时并返回降级答案，而不是整体卡死。这两件事——可判定的失败记录与可读的工具描述——比换更强的模型更能提升系统稳定性，也是我在项目里最有收获的部分。

## 结果

30 条任务集上严格成功率 83.3%、宽松 90%；接入熔断后，单服务故障时任务降级而不是整体超时。项目代码与设计文档都在 GitHub，包含 72 个自动化测试。
